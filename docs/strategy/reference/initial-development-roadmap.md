# ИскИн: первоначальный план развития

**Источник:** `iskin-development-roadmap.md` из Codex-проекта.
**Статус:** исторический справочный материал. Не заменяет актуальный [`../roadmap.md`](../roadmap.md), текущую конкретизацию `v0.5` или отдельные решения.
**Дата фиксации исходного материала:** 2026-09-02.

> Этот документ сохранён для восстановления контекста первоначального планирования. Его последовательность и формулировки не являются актуальным обязательством и не должны применяться вместо канонического roadmap.

## Текущая точка

Budget MVP подтвердил работоспособность ядра agent-native PDLC. Сейчас ИскИн выделяется в самостоятельную универсальную систему для Hermes Agent и Hermes Desktop.

Hermes готовит черновик первого устанавливаемого пакета `v0.3`: универсальные процессные документы, пустую проектную память, телеметрию, шесть обобщённых навыков, устанавливаемый `AGENTS.md` и контракт установки.

## Общая траектория

```text
Budget-эксперимент
        ↓
ИскИн v0.3 — первый устанавливаемый пакет
        ↓
Проверка установки в чистом Hermes-проекте
        ↓
Фиксация main и выпуск v0.3.0
        ↓
Ветка experiment/v0.4
        ↓
Улучшение ядра и Hermes-интеграции
        ↓
Второй продуктовый полигон
        ↓
Следующая версия ИскИн
```

## Этап 1. Проверить черновик пакета v0.3

После завершения работы Hermes проверить:

- отсутствие Budget, P0-01—P0-05, G1—G5, Swift и Xcode в универсальном пакете;
- согласованность документов и навыков;
- отсутствие заполненных продуктовых данных в шаблонах памяти;
- понятный стартовый сценарий после установки;
- отсутствие лишнего дублирования правил;
- сохранение lifecycle-состояний `blocked` и `reopened`, provenance и human gates.

Если обнаружены проблемы, выполнить один ограниченный корректирующий цикл.

## Этап 2. Реализовать установщик v0.3

Установщик должен:

- принимать путь новой папки;
- разрешать несуществующую, пустую папку или папку только с `.git`;
- проверять версию и SHA-256 пакета;
- копировать только содержимое `package/template/`;
- никогда не перезаписывать существующие файлы;
- при необходимости выполнять локальный `git init`;
- создавать `.iskin/version` и installation manifest;
- проверять установленную структуру;
- при ошибке оставлять целевую папку в исходном состоянии;
- не создавать commit, remote или push;
- не устанавливать зависимости и не менять глобальные настройки.

Сначала установщик работает с локальным пакетом. GitHub Release подключается после проверки установки.

## Этап 3. Проверить установку в чистом проекте

### Техническая проверка

- все обязательные файлы установлены;
- лишние и экспериментальные файлы не перенесены;
- повторная установка безопасно останавливается;
- повреждённый пакет отклоняется;
- частичная ошибка не оставляет сломанный проект.

### Поведенческая проверка в Hermes Desktop

- папка открывается как отдельный Hermes Desktop Project;
- Hermes читает правильный корневой `AGENTS.md`;
- обнаруживает шесть проектных навыков;
- не наследует сведения о Budget;
- начинает с формирования продуктового intent;
- не переходит к реализации до необходимых решений человека;
- правильно объясняет границы своих полномочий.

Эта проверка также должна показать, воспроизводится ли U-003 в чистом проекте.

## Этап 4. Зафиксировать стабильную v0.3

После успешной установки:

- привести репозиторий в согласованное состояние;
- создать первый commit;
- изменить версию `0.3.0-draft` на `0.3.0`;
- создать тег `v0.3.0`;
- подключить GitHub remote;
- подготовить GitHub Release с архивом и SHA-256.

`main` содержит только проверенную стабильную версию. Внешняя публикация выполняется после отдельного человеческого решения.

## Этап 5. Начать experiment/v0.4

Создать отдельную ветку `experiment/v0.4` от стабильного тега `v0.3.0`.

Основные направления v0.4:

### Снижение повторной работы

- уменьшить число доказательств, инвалидируемых небольшим локальным изменением;
- уточнить границы evidence scopes без появления слепых зон;
- не допускать повторной проверки независимых результатов без фактической зависимости.

### Работа с ограничениями Hermes

- улучшить контрольные точки длительной работы;
- упростить продолжение после tool-call limit;
- учитывать остаток работы и технические возобновления;
- улучшить использование Hermes Desktop и проектных навыков;
- разобраться с U-003, не смешивая tooling-gap с продуктовой доказанностью.

### Автоматизация метрик и provenance

- автоматически создавать run ID;
- рассчитывать SHA-256;
- проверять связи manifest, report и proof-record;
- обнаруживать drift;
- считать повторные запуски, invalidated proofs и ограничения инструментов;
- формировать согласованное итоговое состояние.

Каждое улучшение начинается с отдельной гипотезы, измеримого ожидаемого эффекта и проверки отсутствия ухудшения обязательного качества.

## Этап 6. Второй продуктовый полигон

Второй полигон начинается после появления одного-двух проверяемых улучшений v0.4.

Он должен отличаться от Budget MVP и проверить:

- установку ИскИн с нуля;
- переносимость процесса на другой продукт и toolchain;
- автономный выбор траектории;
- уменьшение повторной работы, tool-вызовов и технических возобновлений;
- отсутствие ухудшения качества и воспроизводимости.

Другие люди пока не подключаются, но интерфейс, документация и установка проектируются для будущего использования без устного контекста авторов.

## Разделение ответственности

| Участник | Ответственность |
|---|---|
| Человек | Цель ИскИн, значимые границы, принятие версий и внешняя публикация |
| Hermes | Реализация пакета, установщика, проверок и улучшений |
| Методологический партнёр | Проектирование эксперимента, анализ отчётов, выявление развилок и подготовка промтов |

## Ближайшая последовательность

1. Дождаться отчёта Hermes о черновике пакета.
2. Проверить пакет и при необходимости провести один корректирующий цикл.
3. Реализовать установщик.
4. Проверить чистую установку и поведение Hermes Desktop.
5. Зафиксировать и выпустить `v0.3.0`.
6. Создать `experiment/v0.4` и начать оптимизацию ядра.

До проверки установки не начинать одновременно `v0.4` и второй полигон: иначе изменения ядра, упаковки и проверки смешаются, и причины результата будет невозможно восстановить.
