# Минимальная архитектурная спецификация: Git checkpoint experiment v0.4

**Статус:** утверждённая спецификация первого эксперимента; не реализация
**Связанное решение:** `docs/decisions/2026-09-06-v0.4-git-checkpoint-experiment.md`

## Цель

Проверить, что новая независимая сессия Hermes восстанавливает состояние одного product sandbox из Git и durable project state, а не из содержательной подсказки человека или transcript как источника истины.

Эксперимент не проверяет безопасность, второй полигон, внешних пользователей, release, установщик или универсальную Git-политику установленного ядра.

## Границы среды

| Среда | Роль | Что не смешивается |
|---|---|---|
| Репозиторий разработки ИскИн | Документация и будущая разработка v0.4 | Не является product sandbox |
| Основной профиль Hermes | Будущий global runtime навыков ИскИн | Не хранит product state как источник истины |
| Один Git-based product sandbox | Product files, state, evidence, telemetry, checkpoint commits | Не содержит локальных копий навыков ИскИн |
| Другой проект / stable v0.3 | Контроль неизменности | Не используется для восстановления sandbox |

Перед запуском глобальных skills требуется отдельное разрешение человека; эта спецификация его не даёт.

## Durable recovery input

Новая сессия обязана читать следующие источники в указанном порядке и сопоставлять их по project identity и provenance:

1. Git branch, `HEAD`, status и diff;
2. product memory, включая active outcome и lifecycle;
3. evidence, provenance и proof records;
4. telemetry последнего завершённого шага и следующего допустимого действия;
5. process policy и действующие границы полномочий;
6. версию или revision использованных skills.

Transcript Hermes может пояснять контекст, но не меняет state без durable product record и не заменяет read-back фактических внешних действий.

## Контракт checkpoint

Это каноническая модель Git checkpoint для первого эксперимента v0.4 и его global skills.

До любого human approval действует отдельный pre-approval checkpoint contract. Registry находится в `product-memory/approval-packages.md`, а полный пакет — в отдельном `product-memory/approval-packages/<package_id>.md`; он получает уникальный `package_id` и `package_paths`, а затем фиксируется отдельным локальным commit до показа человеку. Hermes показывает весь пакет, package ID и checkpoint SHA только после этого commit; approval event принимается только в следующем человеческом ходе и ссылается на те же package ID и SHA. `checkpoint_sha` не записывается в сам пакет.

Pre-approval checkpoint содержит только process/product description и durable discovery state. Продуктовый код, product evidence, proof-record и `evidence/runs/` делают checkpoint непригодным. Пакет только в dirty tree или уже начатая реализация блокируют retroactive checkpoint и классифицируются как `process-blocked`.

- Чистое рабочее дерево означает, что `HEAD` — последний устойчивый checkpoint законченного перехода.
- Грязное рабочее дерево означает возможное прерывание между checkpoint. Незавершённые изменения сначала исследуются и проверяются; их нельзя слепо удалять, откатывать, stage-ить или commit-ить.
- Локальный checkpoint-коммит создаётся только после проверенного перехода и включает согласованные product files, outcome/lifecycle, evidence/provenance, telemetry, next action и authority boundaries.
- Внешние Git-действия — remote update, push, tag, merge и публикация — не входят в checkpoint model и требуют отдельного решения человека.

До commit применяются все обязательные для перехода product checks, read-back записей, staged-scope review и `git diff --cached --check`.

## Сценарий A — восстановление после checkpoint

### Предусловия

- создан один Git-based product sandbox;
- sandbox не содержит локальных копий ИскИн skills;
- global skills, если они потребуются, были ранее установлены только по отдельному human decision;
- утверждён небольшой bounded outcome и его полномочия;
- зафиксированы baseline состояния другого проекта и stable v0.3.

### Последовательность

1. Hermes начинает outcome.
2. Hermes завершает один связный переход и выполняет применимые проверки.
3. Hermes обновляет product state, actual evidence/provenance и telemetry завершённого шага.
4. Hermes перечитывает записанные данные, проверяет staged scope и создаёт локальный checkpoint-коммит.
5. Сессия завершается планово.
6. Новая независимая сессия открывает тот же sandbox без содержательной подсказки человека.
7. Она выполняет recovery contract.
8. Она находит active outcome и lifecycle, проверяет актуальность evidence, выбирает следующий допустимый шаг и не повторяет актуальное evidence без причины.

Плановое завершение и открытие сессии — часть теста, а не содержательное human steering.

### Проверяемый результат

- восстановлены правильные outcome и lifecycle;
- выбран правильный next action;
- чистый `HEAD` распознан как устойчивый checkpoint;
- актуальное evidence reused либо явно объяснена необходимая повторная проверка;
- recovery не использует state другого проекта;
- нет push, remote, tag, merge или публикации.

## Сценарий B — прерывание между checkpoint

### Предусловие

Сценарий A завершён и оставил проверенный checkpoint. Hermes начинает следующий связный переход.

### Последовательность

1. Hermes начинает следующий переход и создаёт относящиеся к нему незакоммиченные изменения.
2. Сессия намеренно завершается до checkpoint-коммита.
3. В sandbox остаётся грязное рабочее дерево.
4. Новая независимая сессия открывает проект и выполняет recovery contract.
5. Она обнаруживает dirty state и не удаляет, не откатывает, не stage-ит и не commit-ит его вслепую.
6. Она различает: фактически завершённые действия, незавершённые действия, непроверенные побочные эффекты и evidence gaps.
7. В зависимости от проверяемых фактов и authority boundary она безопасно продолжает, повторяет безопасную необходимую проверку либо эскалирует подтверждённый blocker.

### Проверяемый результат

- незавершённые изменения не потеряны;
- новый commit не создаётся до выполнения checkpoint contract;
- не маскируется неизвестный результат внешнего действия;
- решение о продолжении, повторной проверке или escalation следует фактам и полномочиям;
- state другого проекта не используется.

## Телеметрия первого прогона

В обоих сценариях фиксируются без заранее заданных численных порогов:

- содержательное human steering;
- обязательные human escalations и их причины;
- tool calls и elapsed time;
- количество прерываний и успешных recovery;
- reused evidence и лишние повторные проверки;
- rework;
- invalidation, включая подтверждённую interface incompatibility;
- version/revision skills, использованных при evidence и telemetry;
- случаи смешения project state — ожидаемое значение `0`.

## Acceptance criteria эксперимента

Эксперимент считается успешно завершённым только если evidence подтверждает одновременно:

1. правильное восстановление outcome и lifecycle;
2. выбор правильного следующего шага;
3. отсутствие лишнего повторения актуального evidence;
4. сохранность незавершённых изменений в сценарии B;
5. отсутствие использования постороннего project state;
6. создание checkpoint-коммита только после применимых проверок;
7. отсутствие push и иных внешних Git-действий;
8. неизменность `main`, `v0.3.0` и stable v0.3;
9. измерение human steering, tool calls, времени, rework и причин escalations.

Отсутствие численных baseline не является PASS или FAIL: пороги определяются только после первого измерительного прогона отдельным human decision.
