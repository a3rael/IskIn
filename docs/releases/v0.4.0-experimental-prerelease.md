Каноническое решение о границе выпуска: [`2026-09-13-v0.4-experimental-prerelease.md`](../decisions/2026-09-13-v0.4-experimental-prerelease.md).

## 1. Простые итоги

### Что такое ИскИн

ИскИн — универсальная система для Hermes Agent и Hermes Desktop. Она помогает агенту доводить утверждённое продуктовое намерение до проверяемого результата в согласованных границах.

ИскИн — не Telegram-бот и не готовое бизнес-приложение. Он даёт процесс: human gates (обязательные решения человека), состояния результата, проверяемые evidence, происхождение evidence и восстановление состояния проекта.

### Что появилось в v0.4

В v0.4 появились и были закреплены:

- отдельная immutable product specification (неизменяемая утверждённая спецификация) и append-only lifecycle state (история жизненного цикла, которая только дополняется);
- Git-based checkpoint и recovery (контрольная точка и восстановление) для проекта;
- executable policy gate (исполняемый защитный гейт), который должен останавливать недопустимые действия;
- provenance, fingerprints и invalidation events — происхождение evidence, отпечатки входов и явная фиксация устаревших доказательств;
- namespaced global skill bundle из шести `iskin-*` навыков, распространяемый отдельно от устанавливаемого шаблона;
- режим installer для package без project-local skills, без автоматического изменения Hermes configuration.

Наличие этих механизмов не означает, что каждый из них полностью доказан в одном продуктовом сценарии.

### Что показал эксперимент с Telegram-ботом

Эксперимент показал следующее:

- локальная реализация и защитные границы прошли актуальный G1;
- один реальный allowlisted/private `/today` прошёл через Telegram long polling, прочитал Apple Reminders и отправил ответ;
- отдельный read-only G4 получил два redacted объекта из списка Reminders;
- отдельный G5 CRUD-runner выполнил создание, read-back, изменение, завершение, удаление и финальный read-back отсутствия;
- небезопасные или неподходящие Telegram-обновления останавливались fail-closed, а история неудачных попыток не переписывалась.

Это подтверждение отдельных gates, а не приёмка всего Telegram-бота.

### Что пока работает недостаточно хорошо

- нет единого доказанного сквозного MVP-сценария через Telegram с мутациями и подтверждениями;
- O1/O2 не имеют такой же полной lifecycle closure (закрытой записи жизненного цикла), как O3;
- межсессионное recovery и reuse evidence (повторное использование актуального evidence) не подтверждены независимым durable-свидетельством;
- telemetry не позволяет честно посчитать сессии, вмешательства человека, лишние эскалации, tool calls, время и технические возобновления;
- фактическая загрузка global skills в новой Hermes Desktop-сессии не имеет отдельного достаточного evidence;
- запуск зависит от ручной внешней подготовки Keychain/config и постоянно работающего Mac;
- сохраняется известный G4 provenance gap.

Отсутствие записи означает `неизвестно`, а не ноль. Поэтому количественные показатели, которых нет в durable telemetry, здесь не приводятся.

### Что означает экспериментальный статус

Экспериментальный prerelease означает, что:

- текущая v0.4 сохраняется как исходная версия для дальнейшего обучения и сравнения с будущими улучшениями;
- известные сбои, blocked runs и invalidation events остаются видимыми;
- `proved` не считается `accepted`;
- частично доказанный MVP не считается стабильным продуктом;
- выпуск предназначен для контролируемого эксперимента, а не для заявления о production readiness.

### Что будем улучшать в v0.5

Главный приоритет — контроль завершённости задач и актуальности доказательств. Сначала нужно сделать так, чтобы новая сессия могла однозначно ответить:

1. какой outcome сейчас активен и действительно ли он завершён;
2. какие обязательные гейты закрыты;
3. какие evidence относятся к текущему состоянию и revision;
4. какие доказательства устарели и какой следующий шаг допустим.

Другие улучшения — минимальная telemetry вмешательств и безопасный preflight реального запуска — следуют после этого приоритета.

## 2. Что подтверждено и что не подтверждено

| Область | Подтверждено | Не следует утверждать |
|---|---|---|
| ИскИн v0.4 | Есть ядро процесса, policy gate, provenance-модель, lifecycle-события и глобальные навыки | Что все механизмы полностью доказаны в одной сессии |
| G1 | `g1-local-009` — актуальный локальный pass: 32 теста и compile/syntax checks | Что он доказывает Telegram, Keychain или Apple Reminders |
| G3 | `g3-telegram-20260912T190629Z-3a2d5758` — один реальный read-only `/today` | Что весь Telegram command surface или мутации приняты |
| G4 | `g4-read-002` — read-only adapter call, 2 redacted объекта, без мутаций | Что доказаны все реальные команды чтения или полная provenance-цепочка внешнего источника |
| G5 | `g5-crud-001` — CRUD с read-back и cleanup | Что через Telegram доказан confirmation flow |
| Lifecycle | O3: `approved → in-progress → evidence-pending → proved` | Что O3 или весь MVP имеют `accepted` |
| Evidence | 21 run-scoped evidence attempt и 8 invalidation events сохранены в target | Что это 21 вмешательство человека, 21 сессия или 21 лишний повтор |

G4 важно читать в двух слоях: его `proof-record` сообщает `provenance_valid: true` для конкретного run, но release не распространяет это на полный продуктовый сценарий. Redaction и отсутствие O1 lifecycle closure образуют известный release-level provenance gap (разрыв на уровне выпуска).

## 3. Технические ссылки и revisions

### 3.1 Исходные revisions

Для payload (состава устанавливаемого ядра) зафиксирован кодовый anchor:

- source preparation HEAD до этого документа: `7db3ffceecd6ded3db2ad6f53ec0ed63fae82a6d`;
- source commit: `45bd41eaef46afff9d502b03f1fabdd1e13b5960`;
- package tree: `d09222a44b7c70b67e3800745c66c48a3aa108e6`;
- installer tree: `9a0ab641500c60d4091921cce8d8a01445b02801`;
- global skills tree: `2d1bd840b36fdd5847d79626601dbd5e0d9b75d6`;
- global bundle: ровно шесть файлов `runtime/skills/iskin-*/SKILL.md`.

После этого anchor в source были добавлены только документальные изменения; перед фактической сборкой нужно зафиксировать полный final source commit и повторно подтвердить, что `package/`, `installer/` и `runtime/skills/` не изменились.

Состояние экспериментального target, использованное в ретроспективе:

- target HEAD: `fe06c2868e1ffbdf06713ccb923c267a4e7ce03e`;
- ветка: `main`;
- remote: отсутствует.

Эти target-данные — provenance ретроспективы, а не содержимое release-пакета.

### 3.2 Известная граница global skills

Устанавливаемый package не должен содержать `.hermes/skills/` или `.agents/skills/`: global skills распространяются отдельно. Перед публикацией необходимо проверить и записать:

1. точный commit/tree revision global bundle;
2. полный список шести имён;
3. SHA-256 каждого `SKILL.md` либо отдельный проверяемый manifest bundle;
4. что пакет и global bundle взяты из совместимой source revision;
5. что installation manifest не создаёт видимость, будто global skills установлены в проект.

Текущий experiment не доказал фактическую загрузку каждого global skill в новой Hermes Desktop-сессии. Это остаётся ограничением, а не основанием для выдуманного runtime PASS.

## 4. Точный план выпуска

План ниже предназначен для отдельного согласования и не выполнялся в текущей задаче.

### Шаг A. Freeze и preflight

1. Перейти в source repository и подтвердить `git branch --show-current` → `v0.4`.
2. Подтвердить чистое рабочее дерево: `git status --short` не должен вернуть строк.
3. Зафиксировать final source commit после всех разрешённых docs changes.
4. Проверить, что `main`, `v0.3.0`, экспериментальный target, Hermes configuration и global runtime не изменяются.
5. Проверить, что package payload, installer и `runtime/skills/` совпадают с заявленными revisions или явно обновить release decision до сборки.

### Шаг B. Static и release checks

В фактическом выпуске выполнить и сохранить результаты:

```text
python3 tools/verify_repository.py
python3 -m unittest installer/test_verify_release.py -v
python3 -m unittest discover -s installer -p 'test_*.py' -v
python3 -m py_compile installer/install-iskin.py installer/verify_release.py installer/build_release.py installer/test_verify_release.py installer/test_install_iskin.py installer/test_build_release.py
python3 -m py_compile tools/verify_repository.py
```

Ожидается PASS всех применимых проверок. Для docs-only checkpoint текущей задачи применяются только проверки Markdown и Git из development policy; release/test-команды выше намеренно не запускались.

### Шаг C. Сборка release-комплекта

В новом пустом каталоге вне source repository выполнить:

```text
python3 installer/build_release.py \
  --release-version 0.4.0 \
  --output-dir /path/to/empty/iskin-v0.4.0-release
```

Ожидается ровно три файла:

```text
iskin-v0.4.0.zip
install-iskin.py
SHA256SUMS
```

После сборки зафиксировать SHA-256 архива и установщика из `SHA256SUMS` и отдельного read-back. Не принимать прежний hash архива автоматически: новая сборка должна быть проверена заново.

### Шаг D. Read-only validation и пробная установка

1. Передать в validator именно версию `0.4.0`, путь нового архива и фактический SHA-256:

```text
python3 installer/verify_release.py \
  --archive /path/to/empty/iskin-v0.4.0-release/iskin-v0.4.0.zip \
  --release-version 0.4.0 \
  --expected-sha256 <ARCHIVE_SHA256_FROM_SHA256SUMS> \
  --report /path/to/empty/iskin-v0.4.0-release/verify-report.json
```

2. Проверить, что validator подтвердил имя, SHA-256, `VERSION`, manifest schema v1, полный allowlist, отсутствие опасных путей и запрещённых product-specific материалов.
3. Установить только в новый временный probe-project:

```text
python3 /path/to/empty/iskin-v0.4.0-release/install-iskin.py \
  --archive /path/to/empty/iskin-v0.4.0-release/iskin-v0.4.0.zip \
  --release-version 0.4.0 \
  --expected-sha256 <ARCHIVE_SHA256_FROM_SHA256SUMS> \
  --target-path /tmp/iskin-v0.4.0-probe \
  --init-git
```

4. Read-back должен подтвердить `.iskin/version`, `installation-manifest.json`, установленные байты и отсутствие commit/remote/tag/push со стороны installer. Probe-project после проверки удалить только отдельным разрешённым housekeeping-шагом; секреты туда не помещать.
5. Отдельно убедиться, что installer не выполнял `hermes skills trust`, не менял profile/configuration/gateway и не устанавливал global skills.

### Шаг E. Детерминированность и согласованность каналов

1. Собрать тот же source и версию второй раз в другом пустом output directory.
2. Сравнить байты ZIP, standalone installer и `SHA256SUMS`; ожидается побайтовое совпадение.
3. Сравнить файлы probe-project с `package/template/` и SHA-256 из manifest.
4. Сверить package manifest с глобальным bundle manifest: package не содержит global skills, а bundle содержит ровно шесть `iskin-*` skills из зафиксированной revision.
5. В release record записать: final source commit, package/installer/skills revisions, archive SHA-256, installer SHA-256, результаты validator и trial install.

### Шаг F. Предлагаемые Git-действия и публикация

После отдельного разрешения человека предлагается такой порядок:

1. оставить текущие document changes в локальном docs checkpoint;
2. зафиксировать final source commit для release candidate;
3. выполнить проверки A–E и сохранить их read-back;
4. создать tag `v0.4.0` только после успешных проверок и отдельного разрешения;
5. подготовить GitHub Release с пометкой **Prerelease**, не **Latest/stable**;
6. приложить ровно `iskin-v0.4.0.zip`, `install-iskin.py`, `SHA256SUMS` и понятное описание из раздела 1;
7. явно перечислить G4 provenance gap, отсутствие полной Telegram mutation proof, отсутствие полного recovery evidence и отсутствие `accepted`;
8. только после отдельного разрешения выполнить push ветки/tag и публикацию Release;
9. после публикации прочитать обратно tag, Release metadata и все три asset names/hashes.

Текущая задача не разрешает ни один из шагов 4–9. Main и `v0.3.0` должны остаться без изменений.

## 5. Результат текущего действия

Подготовлены decision, release brief и указатели в roadmap. Не выполнялись release build, пробная установка, runtime update, tag, push, merge, GitHub Release, тесты продукта или новые proofs. Следующий шаг — согласование этого плана и отдельное разрешение на фактический release workflow.
