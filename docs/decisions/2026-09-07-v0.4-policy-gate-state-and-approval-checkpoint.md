# ИскИн v0.4: immutable core, append-only approval events и approval checkpoint

**Статус:** локальное архитектурное решение для bounded change после read-only проверки commit `45b0b899723b3730c035f9d5830568b49bf22a07`.

## Решение

1. `package/template/.iskin/policy_gate.py` остаётся immutable installation-managed файлом и фиксируется в installation integrity allowlist.
2. Template-файл `.iskin/policy_state.json` удаляется. Lifecycle и approval state не перезаписываются в установленном core.
3. Канонический machine-readable approval event создаётся в `product-memory/approval-events/<event_id>.json`. Event schema versioned (`schema_version: 1`) и append-only: новый approval получает новый event ID/path.
4. `product-memory/decisions.md` хранит human-readable ссылки на `approval_event_id`, `approval_event_path`, `package_id` и `checkpoint_sha`. Gate проверяет согласованность, но не выдаёт её за криптографическое доказательство авторства человека или факта показа conversational package.
5. Установочный `installation-manifest.json` сохраняет schema v1 и содержит только immutable installation core и `.iskin/version`. Template payload остаётся полным release package manifest v1; `product-memory/` и `telemetry/` устанавливаются, но их рабочие изменения не являются повреждением immutable core.
6. После human approval используется отдельный action `approval_checkpoint`. Он разрешается только при точном staged scope: один новый event и `product-memory/decisions.md`, без unstaged/untracked посторонних изменений, package drift, product code/evidence и с успешным `git diff --cached --check`. Сам commit технический и не создаёт нового human gate.
7. После approval checkpoint `change_product`, `prove_result` и обычный `checkpoint` разрешаются только при `IMPLEMENTATION_ALLOWED`. До него product implementation и proof запрещены.
8. Отсутствующий gate, legacy policy state или неподдерживаемая event schema дают `PROCESS_BLOCKED` с reason `UNSUPPORTED_PROJECT_STATE`. Старые проекты не мигрируются автоматически в этом изменении.

## Exit semantics

`status` и `read_only_recovery` могут вернуть диагностический отчёт о blocked state с exit `0`. Action-gate возвращает exit `0` только когда запрошенное действие разрешено. Skills проверяют одновременно exit code и machine-readable status. Это измеряемое ограничение v0.4, а не capability broker, Git hook или OS-level enforcement.

## Проверяемые границы

Машинно проверяются schema, event history, Git order, exact package/checkpoint IDs and paths, staged scope, package drift, product code/evidence before approval, installation SHA integrity и action-specific permission. Conversational факт показа пакета и реальное human authorship остаются human evidence boundary.

## Не входит в решение

Не добавляются capability broker, Git hooks, OS-level enforcement, автоматическая migration старых sandbox, runtime update, release publication, push, tag или remote operation.
