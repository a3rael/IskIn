# Наблюдение v0.4: bootstrap checkpoint до первого commit

## Наблюдение

В новой установке ИскИн с `--init-git` до initial commit все release-файлы находятся в untracked scope. Старый executable policy gate применял общий классификатор product evidence к `process/fixtures/provenance-drift/template/proof-record.json` и возвращал `PROCESS_BLOCKED / PRODUCT_OR_EVIDENCE_WITHOUT_PACKAGE`. После технического initial commit это ошибочно выглядело исправленным только потому, что файл уже находился в `HEAD`.

## Причина

До первого commit у gate не было отдельного проверенного installation baseline. Поэтому provenance process fixture не отличался от фактического product evidence по происхождению и Git scope.

## Решение

В установленный immutable core добавлен `.iskin/bootstrap-manifest.json`. Он перечисляет baseline-файлы по полным относительным путям и SHA-256. Gate использует его вместе с `.iskin/installation-manifest.json`, проверяет exact inventory, baseline hashes, пустые mutable project memory/telemetry, отсутствие approval/product state и exact staged scope.

Добавлено действие `bootstrap_checkpoint`. Оно доступно только при отсутствии `HEAD`, валидном verified baseline и полностью staged baseline. Lifecycle status не расширен: до commit возвращается `DISCOVERY_ALLOWED` с `INITIAL_BASELINE_UNCOMMITTED`; после commit остаётся discovery. Gate остаётся read-only и не staging-ит/не commit-ит.

Отдельного исключения для `proof-record.json` нет: process fixture считается baseline только как путь и содержимое verified manifest. Изменение, удаление, подмена или дополнение файлов переводит bootstrap в fail-closed состояние.

## Проверки

Покрыты сценарии точной установки, fixture provenance, product/evidence/unexpected files, изменённого и отсутствующего baseline, неправильного staged scope, exact staged baseline, post-commit discovery, запрета product actions и read-only поведения gate. Дополнительно проверяется полный локальный flow:

```text
release → install --init-git → policy gate → bootstrap checkpoint → clean discovery state
```

Bootstrap commit является только технической локальной исходной точкой. Он не является product checkpoint, approval или разрешением реализации; remote, push, tag и внешняя публикация не выполняются.

## Дополнительное наблюдение: authorization staging gap

Первый реальный новый sandbox показал отдельный пробел: до staging gate возвращал `DISCOVERY_ALLOWED` и разрешал discovery, но не выдавал машинного разрешения на exact staging. Тестовый helper напрямую выполнял `git add -A`, поэтому прежний полный flow скрывал отсутствие authorization-перехода в живой orchestration.

Контракт исправлен отдельным статусом `BOOTSTRAP_REQUIRED` и read-only action `stage_bootstrap_baseline`. Gate возвращает exact `allowed_paths`, но не меняет index. Orchestration обязана stage-ить только этот список, перечитать staged scope и затем вызвать `bootstrap_checkpoint`; любой неполный, расширенный или изменённый scope fail closed. Discovery и approval preparation становятся доступными только после технического initial commit.
