# Решение: ИскИн v0.4.0 как обычный текущий релиз

**Дата:** 2026-09-13
**Статус:** утверждено человеком
**Тип:** human decision о статусе опубликованного релиза

## Решение

1. ИскИн `v0.4.0` становится обычным опубликованным релизом, Latest и рекомендуемой текущей основой.
2. Дальнейшее развитие ведётся в направлении `v0.5`.
3. Это решение заменяет прежнее решение от `2026-09-13` только в части экспериментального статуса и канала публикации. Историческое решение [`2026-09-13-v0.4-experimental-prerelease.md`](2026-09-13-v0.4-experimental-prerelease.md) не переписывается.
4. Release остаётся честным описанием ограниченного, проверенного состава. Обычный статус не означает доказанную полную автономность, отсутствие ошибок или принятие продуктового эксперимента с Telegram-ботом.
5. Сохраняются ограничения evidence и lifecycle, неполное доказательство восстановления между сессиями, неполная telemetry и все явно описанные границы внешнего эксперимента.
6. Исторический G4 pass остаётся историческим: различие fingerprint `bot/reminders.py` в manifest и текущем файле является provenance gap. Redaction и отсутствие lifecycle closure остаются отдельными вопросами.
7. Отсутствие live Telegram CRUD остаётся границей проверки, а не нарушением утверждённых критериев эксперимента.

## Граница решения

Разрешены:

- обновление актуальной документации и указателей;
- локальный development-only docs checkpoint по действующей policy;
- обычный fast-forward push ветки `v0.4`;
- обновление metadata и описания уже существующего GitHub Release `v0.4.0` без пересоздания Release, перемещения тега или замены assets;
- назначение существующего Release `Latest` и снятие отметки `Prerelease`.

Не разрешены этим решением:

- изменение target тега `v0.4.0`;
- замена или пересборка release assets;
- изменение `package/`, `runtime/skills/`, installer-кода, Hermes runtime или экспериментального проекта бота;
- изменение `main` или `v0.3.0`;
- merge, force push, переписывание Git-истории или создание нового Release.

## Основания и границы доказательства

Техническая подготовка release-комплекта, validator, пробная установка, read-back и побайтовая проверка трёх assets уже выполнены для release commit `b94b8bc2f7f8cc1c3dda0f4448c7043f39ca9024`. Смена статуса не расширяет область этих доказательств и не превращает экспериментальные product evidence в `accepted`.

Рекомендуемая текущая основа означает, что для нового развития следует брать опубликованный `v0.4.0`, а новые продуктовые и процессные изменения планировать в `v0.5`. Любые новые claims требуют собственных актуальных проверок и provenance.
