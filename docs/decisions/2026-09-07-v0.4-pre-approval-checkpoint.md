# Решение v0.4: pre-approval Git checkpoint

**Дата:** 2026-09-07
**Статус:** process contract v0.4; checkpoint создаётся до показа и approval
**Связано с:** `docs/decisions/2026-09-06-v0.4-first-run-approval-observation.md`

## Причина

Первый полный эксперимент показал, что единый approval barrier недостаточно защищает от утверждения пакета, который человек фактически не видел. Между подготовкой package и human question отсутствовала immutable revision, на которую можно было бы ссылаться после показа.

## Решённый lifecycle

```text
discovery
→ полный approval package в product-memory/approval-packages/<package_id>.md
→ pre-approval checkpoint commit
→ показ всего пакета, package ID и checkpoint SHA
→ один прямой human question
→ ответ в следующем человеческом ходе
→ durable approval event
→ реализация
```

Pre-approval checkpoint не является approval, acceptance или разрешением реализации. Он только фиксирует immutable revision пакета до его показа.

## Канонический артефакт

`product-memory/approval-packages.md` — registry полных пакетов. Каждый пакет хранится отдельным immutable-файлом `product-memory/approval-packages/<package_id>.md`, поэтому добавление нового пакета не изменяет package-файлы прежних approvals. Запись содержит:

- уникальный `package_id`;
- `package_paths` для проверки drift;
- intent и ценность;
- границу MVP: входит и не входит;
- outcomes и наблюдаемое поведение;
- обязательные gates и evidence scopes;
- uncertainties, риски, зависимости и ограничения.

`checkpoint_sha` не записывается в package-файл внутри создаваемого checkpoint commit. Его значение появляется только в последующем approval event.

## Scope checkpoint

Pre-approval checkpoint может содержать только process/product description и durable discovery state. В него не входят:

- продуктовый код;
- product evidence;
- proof-record;
- каталоги `evidence/runs/`;
- другие последствия реализации.

Пакет только в dirty tree не даёт полномочий реализации. Если код или evidence появились до checkpoint, задним числом checkpoint не создаётся; recovery сохраняет изменения и возвращает `process-blocked`.

## Approval event

Event записывается в существующий `product-memory/decisions.md` только после фактического показа всего пакета и в следующем человеческом ходе. Он обязан ссылаться на те же package ID и checkpoint SHA и содержать:

```text
package_displayed_in_previous_agent_turn: true
package_id: <package ID>
checkpoint_sha: <checkpoint SHA>
approval_question: <фактически заданный вопрос>
human_response: <фактический ответ>
actor: <actor>
implementation_authorized: true
```

Фраза «авторизую полный пакет» без доказанного показа недействительна. Generic «продолжай», discovery-ответ и разрешение отдельного технического действия не являются lifecycle approval. Hermes не предлагает человеку готовый ответ, утверждающий не показанный пакет.

## Drift

До реализации recovery проверяет, что содержимое каждого `package_path` байтово совпадает с revision checkpoint. Изменение любого package path делает прежний approval недействительным. Требуются новый package ID или revision, новый checkpoint, повторный показ и новый human approval. История не переписывается.

## Граница enforcement

- Process contracts и global skills задают обязательный порядок и authority boundary.
- Repository verifier проверяет наличие канонического артефакта и обязательных маркеров template contract.
- Contract tests покрывают отрицательные и положительные сценарии.
- Фактический runtime должен применять эти правила через recovery/read-back; текстовый документ сам по себе не является программным блокировщиком.

## Проверяемые сценарии

Контракт требует блокировать: отсутствие package, package только в dirty tree, checkpoint с кодом, непоказанный пакет, generic continuation, техническое разрешение и drift после checkpoint. Разрешён только пакет, показанный перед approval, с совпадающими package ID и checkpoint SHA и явным подтверждением обеих частей human question.
